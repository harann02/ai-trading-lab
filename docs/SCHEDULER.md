# Scheduler reliability (GitHub Actions)
* Calendar: official NYSE via `pandas_market_calendars` (America/New_York, DST, holidays, early closes), displayed in MYT.
* Wide UTC cron + calendar gate: monitor `*/15 13-21 * * 1-5` covers 13:30–20:00 UTC (EDT) and 14:30–21:00 UTC (EST) incl. 25 min post-close; `tools/gate.py` skips off-market runs and records the reason (`status/skips.json` → `job_runs`).
* `job_runs` heartbeat: scheduled-for / started / finished / status (`running|success|failed|skipped`) / reason / run id. Idempotency key per slot or session (`UNIQUE idem_key`) → duplicates are refused and recorded; a crashed `running` row older than 45 min can be retried.
* Single writer: workflow `concurrency: ailab-ledger`, DB lease (`writer_lease`, 25 min expiry) and `writer_mode`.
* Missed-run detection: expected-slot calculator vs actual runs (`app/v3/schedule.py::missed_runs`); skips and duplicates never satisfy a slot. Self-healing: the next monitor run performs a **catch-up scan** if the last session's scan is missing (orders then become eligible the following session; forward verification does not count a catch-up as on-time).
* Watchdog workflow → GitHub issue `scheduler-alert`. Dashboard **Health** tab: status, last scheduled/successful run, next expected, last scan, last reconciliation, market status, data freshness, latest error, failed/skipped counts. **Deployment status (Pages) ≠ engine status (job_runs)** — a green deploy does not prove the engine ran.
* Limit: GitHub cron is best-effort (delays/drops happen, scheduled workflows pause after 60 days of repo inactivity). The design detects and reports; it cannot guarantee.
