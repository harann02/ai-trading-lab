# Scheduler reliability (GitHub Actions)
* Calendar: official NYSE via `pandas_market_calendars` (America/New_York, DST, holidays, early closes), displayed in MYT.
* Wide UTC cron + calendar gate: monitor `4,19,34,49 13-21 * * 1-5` (off-grid; scan slot `41 21 * * 1-5`, weekly `13 2 * * 6`) covers 13:30–20:00 UTC (EDT) and 14:30–21:00 UTC (EST) incl. 25 min post-close; `tools/gate.py` skips off-market runs and records the reason (`status/skips.json` → `job_runs`).
* `job_runs` heartbeat: scheduled-for / started / finished / status (`running|success|failed|skipped`) / reason / run id. Idempotency key per slot or session (`UNIQUE idem_key`) → duplicates are refused and recorded; a crashed `running` row older than 45 min can be retried.
* Single writer: workflow `concurrency: ailab-ledger`, DB lease (`writer_lease`, 25 min expiry) and `writer_mode`.
* Missed-run detection: expected-slot calculator vs actual runs (`app/v3/schedule.py::missed_runs`); skips and duplicates never satisfy a slot. Self-healing: a monitor run performs a **catch-up scan** only when the last session's EOD-scan window genuinely lapsed (now ≥ next session open) with no scan recorded (orders then become eligible the following session; forward verification does not count a catch-up as on-time).
* Watchdog workflow → GitHub issue `scheduler-alert`. Dashboard **Health** tab: status, last scheduled/successful run, next expected, last scan, last reconciliation, market status, data freshness, latest error, failed/skipped counts. **Deployment status (Pages) ≠ engine status (job_runs)** — a green deploy does not prove the engine ran.
* Intent-based classification (fix for issue #3): unattended runs (cron `schedule`, external `repository_dispatch`) use `action=auto`; `app/v3/schedule.classify` returns `scan` iff now is in the last session's EOD-scan window [NYSE close + 30 min, next open) (close from the NYSE calendar: DST + early closes) and no successful scan/catch-up scan exists for it and the provider already serves the final daily bar for the session (`final_bars_ready`; otherwise the run is a monitor and the scan is deferred to the next run) and no successful scan/catch-up scan exists for it, else `monitor`. Re-checked under the writer lease in `ci_run.py`; `scan:<session>` idempotency key shared by schedule + external → a delayed or dropped slot still yields the scan, double runs cannot double-scan/double-trade.
* Trigger classes in `job_runs.trigger`: `schedule` (GitHub cron), `external_scheduler` (repository_dispatch `external-cron`, see `docs/EXTERNAL_CRON.md`), `workflow_dispatch`/`push`/`manual`.
* Limit: GitHub cron is best-effort (delays/drops happen, scheduled workflows pause after 60 days of repo inactivity). The design detects and reports; it cannot guarantee.

## EOD scan timing/labelling fix (16 Oct 2026)
* **Incident (15 Oct 2026 session):** an external-backup run (repository_dispatch) at 20:08 UTC, 8 min after the 16:00 ET close, was classified `monitor` (correct) but the monitor path's self-heal saw "no scan yet for the last completed session" and ran a `catchup_scan` immediately — bypassing the EOD window and before final daily bars had settled. The real 21:41 scan then found the session already scanned. Verification labelled the session "scheduled scan missed (catch-up only)".
* **Rule now:** EOD window = [close + 30 min, next open) using the NYSE calendar (EDT 20:30 UTC, EST 21:30 UTC, 13:00 ET early close → 18:30 UTC). The scan also requires the session's final daily bar from the provider. The **first unattended run (github-schedule or external-backup) inside the window is the on-time scan** (`job=scan`); forward verification counts a `scan` as on-time iff it started inside that window. `catchup_scan` happens only after the window lapsed (at/after the next session's open).
* **History is not rewritten:** 12–14 Oct stay failed. 15 Oct stays as recorded ("scheduled scan missed (catch-up only)") because its only scan ran at close + 8 min, before final bars — it is deliberately NOT relabelled as passing.
